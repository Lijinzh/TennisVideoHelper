# TennisVideoHelper GPU 优先性能优化设计

日期：2026-07-25

## 1. 目标与实施顺序

本次优化采用已经确认的两阶段架构：

1. 第一阶段先交付不依赖 NPU 的纯 NVIDIA GPU 极限优化版本。
2. 第二阶段再开发可选的 AMD NPU 插件，并通过同素材基准判断是否值得启用。

第一阶段必须能够独立安装、运行和验证。没有 NPU 的电脑不安装任何 NPU 依赖，也不会看到误导性的“已启用 NPU”状态。第二阶段不得改变第一阶段的默认行为，只有同时满足硬件、运行时和性能收益门槛时才能启用 NPU。

## 2. 当前性能基线与根因

2026-07-24 的完整处理记录如下：

| 输入 | 视频时长 | 处理耗时 | 约合处理速度 |
| --- | ---: | ---: | ---: |
| IMG_0557.MOV，1080P HLG | 18.21 分钟 | 11.22 分钟 | 1.62× 实时 |
| IMG_0558.MOV，1080P HLG | 56.06 分钟 | 34.47 分钟 | 1.63× 实时 |
| VID_20260425_213428.mp4，4K SDR | 22.22 分钟 | 130.28 分钟 | 0.17× 实时 |

运行时采样显示：

- RTX 4060 仅使用约 193 MiB 显存。
- GPU 计算利用率通常为 17% 至 34%，核心频率长期停留在约 210 MHz 的 P8 状态。
- Python 进程平均只使用约两个 CPU 逻辑核心。
- OpenCV Python 包不包含 CUDA 或 NVDEC 支持。

根因不是电源模式，而是现有视觉管线完全串行：

1. `cv2.VideoCapture` 在 CPU 上解码全部源帧。
2. 即使只分析 12 FPS，也会先解码不需要的帧。
3. 每次只向 YOLO 提交一帧，批大小固定为 1。
4. 推理使用默认精度，`quantize=16` 不等价于 FP16 或 INT8 推理。
5. 每帧都同步等待结果，并多次将张量复制回 CPU。
6. 视频之间、音频分析、视觉分析和导出阶段顺序执行。
7. 每个输出片段单独启动 FFmpeg，可能重复打开和解码源视频。

## 3. 第一阶段：纯 GPU 极限版本

### 3.1 总体数据流

```text
媒体探测 ───────────────┐
                        ├─→ 音画融合 → 回合区间 → 批量导出与验证
音频提取与 CPU 分析 ────┤
                        │
NVDEC 抽帧 → GPU 预处理 → TensorRT 批量姿态推理 → 时序后处理
```

音频与视觉分析在视频级别并行运行。视觉内部采用有界流水线，使解码、预处理、推理和后处理能够重叠执行。所有队列必须有容量上限，避免长视频无限占用内存或显存。

### 3.2 NVDEC 硬件解码与抽帧

优先使用 NVIDIA 官方 PyNvVideoCodec 2.x：

- 使用 `ThreadedDecoder` 或等效异步接口读取 HEVC/H.264。
- 在解码阶段直接按分析时间戳抽取需要的帧，不再解码后由 Python 丢弃大量帧。
- 保留每帧真实显示时间戳，继续支持可变帧率视频。
- 8-bit 与 10-bit 输入分别处理，保持 HLG、HDR10 和 Dolby Vision 8.4 基础层策略。
- 解码后尽可能通过 CUDA Array Interface 或 DLPack 交给后续 GPU 阶段，避免完整画面往返 CPU。

如果 PyNvVideoCodec 不支持某个容器、像素格式或时间戳场景，则回退到 FFmpeg `-hwaccel cuda` 管线。只有硬件解码也不可用时才回退到当前 OpenCV 路径，并在 CLI/UI 中明确显示降级原因。

### 3.3 GPU 预处理

缩放、颜色转换、归一化和批次组装应在 GPU 上完成。第一阶段优先选择与 PyTorch/TensorRT 兼容、部署风险较低的实现，不为了理论零复制引入无法稳定安装的复杂依赖。

预处理要求：

- 使用独立 CUDA Stream，与解码和推理重叠。
- 输入尺寸固定为模型需要的 640 像素尺度，便于 TensorRT 优化。
- 使用预分配缓冲区，避免逐帧申请 GPU 内存。
- 只在后处理确实需要时，将紧凑的关键点和检测框结果复制到 CPU。
- 不将完整原始帧长期缓存在显存中。

### 3.4 TensorRT 推理后端

姿态推理从 Ultralytics 逐帧 `predict` 改为独立后端接口，至少包含：

- `TensorRTPoseBackend`：第一阶段默认后端。
- `TorchPoseBackend`：安装或引擎构建失败时的兼容后端。
- `LegacyPoseBackend`：用于结果对照和问题定位，不作为默认路径。

提供两种用户模式：

#### 高精度极速模式

- TensorRT FP16。
- 固定模型输入尺寸。
- 自动批大小，RTX 4060 8 GB 初始候选为 16，并通过短预热自动确定 8、16 或 32。
- 保持现有分析 FPS 和融合参数语义。
- 作为 UI 和 CLI 默认模式。

#### 性能极限模式

- TensorRT INT8，必须使用真实网球视频帧建立校准缓存。
- 允许更大的批次和自适应抽帧。
- 只在输出召回率和边界偏差通过校准集验证后开放。
- UI 必须明确提示可能存在轻微检测结果差异。

TensorRT 引擎必须按 GPU 型号、TensorRT 版本、模型哈希、输入尺寸、精度和批次配置缓存。缓存不匹配时重新构建，禁止加载不兼容引擎。

### 3.5 异步批处理和显存管理

视觉管线使用三个有界阶段：

1. 解码线程将采样帧放入 GPU 帧队列。
2. 批次组装器按批大小或最大等待时间形成推理批次。
3. 后处理器按时间戳顺序恢复检测结果并计算动作事件。

显存策略：

- 默认最多使用约 6.5 GB，给桌面、Qt 和 NVENC/NVDEC 留出余量。
- 根据 `torch.cuda.mem_get_info()` 或等效接口动态降低批次。
- 遇到显存不足时依次尝试 32 → 16 → 8 → 4，禁止直接回退 CPU 并静默继续。
- 使用固定数量的输入、输出和临时缓冲区。
- 任务结束后释放模型、引擎、CUDA Context 和解码器缓存。

### 3.6 光流与动作后处理

现有稀疏光流和关键点选择逻辑必须先保持语义一致，避免性能改造同时改变识别算法。

第一阶段按收益分两步：

1. 先用批量 TensorRT 推理解决最大瓶颈，保留 CPU 光流作为可验证基线。
2. 若分析表明 CPU 光流成为新瓶颈，再评估 CUDA 光流、NVIDIA Optical Flow Accelerator 或减少计算频率。

完整图像不得为每个检测框重复复制。关键点张量应一次性批量传回 CPU，并在 NumPy 中按时间戳顺序处理。

### 3.7 音频与视觉并行

音频提取和视觉分析彼此独立，应并行执行：

- FFmpeg 音频提取在独立子进程中运行。
- CPU 音频特征计算限制线程数，避免抢占解码和 UI。
- 视觉 GPU 管线同时运行。
- 两者完成后再进入融合。

并行调度必须避免 FFmpeg、NumPy、SciPy 和 PyTorch 各自创建过多线程。程序启动时记录有效线程配置，基准阶段再确定最佳值。

### 3.8 导出优化

第一版输出结果必须继续满足分辨率、帧率、色彩、音画同步和验证规则。

导出优化分级实施：

1. 先限制并复用 FFmpeg/NVENC 配置，减少重复环境检查和进程启动成本。
2. 对多个片段使用有界并行导出，初始并发数为 2，并通过显存和编码器利用率验证。
3. 若单视频多片段重复解码仍是显著瓶颈，再使用 PyNvVideoCodec 的 segment-based transcoding 或单次 FFmpeg 管线。

不得为了速度破坏 HLG/HDR10 色彩标记、Dolby Vision 8.4 基础层转换策略、可变帧率时间关系或输出验证。

## 4. UI 与 CLI 设计

当前 PySide6 UI 作为第一阶段的一部分保留，并新增以下能力：

- 加速模式：高精度极速 FP16、性能极限 INT8。
- 后端状态：NVDEC、TensorRT、CUDA、NVENC 是否生效。
- 当前批大小、显存占用、处理 FPS、实时倍速和预计剩余时间。
- 分阶段进度：媒体探测、音频、视觉、融合、导出、验证。
- 降级提示：明确显示回退到 Torch、FFmpeg 或 OpenCV 的原因。
- 高级设置默认折叠，避免普通用户必须理解批次和 CUDA Stream。

CLI 提供与 UI 等价的核心选项，便于自动化和重复基准。UI 继续通过独立后台进程启动分析，避免 GPU 初始化或模型构建阻塞 Qt 主线程。

## 5. 第二阶段：可选 NPU 插件

### 5.1 安装与发现

NPU 支持不得加入基础依赖。项目采用独立可选依赖组或外部插件包，例如：

```text
tennis-video-helper                 # 不含 NPU
tennis-video-helper[npu-amd]        # 仅在支持的 AMD 机器上安装
```

启动时按以下顺序检测：

1. 是否存在受支持的 AMD NPU PCI 设备。
2. NPU 驱动是否满足 Ryzen AI/Vitis AI EP 的版本要求。
3. ONNX Runtime 是否实际列出 `VitisAIExecutionProvider`。
4. 模型编译报告中是否有足够比例的算子分配给 NPU，而不是回退 CPU。
5. 相同素材端到端基准是否快于纯 GPU 版本。

任一步失败都将 NPU 标记为“不可用”或“无性能收益”，主程序继续使用纯 GPU 路径。

### 5.2 NPU 候选任务

NPU 不与 RTX 4060 争抢主姿态推理。优先测试输入/输出体积较小、能和 GPU 同时执行的辅助任务：

- 基于关键点时间序列的动作分类器。
- 量化后的声音候选分类器。
- 低分辨率场景或有效画面门控模型。

这些任务需要独立证明能够减少 GPU/CPU 工作或提高整体吞吐。仅提升任务管理器里的 NPU 利用率不算成功。

### 5.3 NPU 启用门槛

NPU 插件只有在以下条件全部满足时才能默认建议启用：

- 相同输入、相同模式和相同输出规则下，端到端中位耗时至少降低 5%。
- 长回合召回率下降不超过已批准容差。
- 不增加安装后的默认启动失败概率。
- 没有 NPU 的电脑不需要下载任何 NPU 模型、运行时或驱动组件。

如果性能提升不足 5%，NPU 插件不进入默认产品路径；可以保留为实验功能，也可以移除。

## 6. 基准测试设计

### 6.1 固定样本

使用当前三段真实视频作为回归集，并从中确定固定时间窗口：

- 1080P HLG：包含普通运动和多个回合的 5 分钟窗口。
- 4K SDR：包含快速挥拍和背景球场干扰的 5 分钟窗口。
- 完整视频：用于验证长时间稳定性、内存增长和实际总耗时。

### 6.2 测量指标

每次基准记录：

- 总耗时及各阶段耗时。
- 分析视频秒数/墙钟秒数。
- 解码 FPS、推理 FPS、导出 FPS。
- GPU SM、显存、NVDEC、NVENC 利用率。
- CPU 总占用、进程内存峰值和磁盘吞吐。
- 模型后端、精度、批大小和是否发生降级。
- 视觉事件数量、融合事件数量、回合数量和回合边界偏差。

基准数据写入独立 JSON，不与用户最终分析报告混合。

### 6.3 第一阶段验收目标

最低交付标准：

- 1080P 输入端到端速度不低于当前版本的 2 倍。
- 4K 输入端到端速度不低于当前版本的 4 倍。
- 4K 5 分钟窗口能够稳定完成，不发生显存溢出或持续内存增长。
- FP16 模式的长回合召回率不得明显低于当前版本。
- INT8 模式只有在校准集通过后才作为可选模式发布。
- 所有现有单元测试继续通过，并新增性能后端、回退、批次和 UI 参数测试。

目标值不是承诺上限。实际实现若达到更高速度，应保留测量证据，而不是继续增加不必要复杂度。

## 7. 错误处理与回退

- TensorRT 不可安装或引擎构建失败：提示原因并回退 Torch FP16。
- NVDEC 不支持当前输入：回退 FFmpeg 硬件解码，再回退 OpenCV。
- 显存不足：自动降低批次并记录事件。
- INT8 校准缓存缺失：禁止启动 INT8，提示生成流程。
- NPU 缺失、驱动不兼容或无收益：禁用插件，不影响 GPU 主程序。
- 用户停止任务：终止完整后台进程树，并清理未完成临时文件和 CUDA 资源。
- 单视频失败：记录错误并继续处理后续视频。

任何回退都必须显示在日志和 UI 中，不允许静默降低到 CPU 后仍显示“GPU 加速”。

## 8. 测试策略

### 8.1 单元测试

- 自动批大小选择和显存不足降级。
- 帧批次时间戳排序与尾批处理。
- FP16/INT8/Torch 后端选择。
- TensorRT 引擎缓存键和失效条件。
- NVDEC、FFmpeg 和 OpenCV 回退顺序。
- NPU 插件发现、版本检查和收益门槛。
- UI/CLI 参数映射和状态显示。

### 8.2 集成测试

- 1080P 10-bit HLG 输入。
- 4K 8-bit SDR 输入。
- 可变帧率输入。
- NVDEC 不支持的模拟路径。
- TensorRT 引擎首次构建和缓存复用。
- 用户中止、单视频失败和批处理继续。
- HLG/HDR10 输出验证和 Dolby Vision 8.4 基础层策略。

### 8.3 性能回归

性能测试不使用单次结果判定。短窗口至少预热一次、测量三次并报告中位数。若优化提高 GPU 利用率却使端到端耗时增加，则视为失败。

## 9. 分步实施边界

为控制风险，每一步最多集中修改五个非生成文件：

1. 性能计时、基准命令和结果数据结构。
2. 姿态后端接口及 Torch 批量基线。
3. TensorRT FP16 引擎与缓存。
4. NVDEC/PyNvVideoCodec 解码后端。
5. 异步批处理和显存自适应。
6. 音频与视觉并行调度。
7. 导出并行与重复解码优化。
8. UI/CLI 加速模式和性能状态。
9. INT8 校准与性能极限模式。
10. NPU 插件原型和端到端收益审计。

每一步都必须先建立可重复基准或失败测试，再做单一方向修改，最后运行相关测试和真实视频短窗口验证。

## 10. 完成标准

第一阶段完成时必须具备：

- 可独立安装的 GPU-only 版本。
- 默认 TensorRT FP16，具有可靠 Torch 回退。
- 实际生效的 NVDEC/NVENC 与异步批处理。
- 可复现的前后性能数据。
- UI 和 CLI 均能显示真实后端、进度和降级状态。
- 结果准确率和媒体输出规则通过回归验证。
- 不需要 NPU 即可获得主要性能提升。

第二阶段完成与否由实测决定。NPU 插件若无法带来至少 5% 的端到端收益，则不作为正式加速功能发布。
