# 网球长回合自动筛选与视频切分工具设计

日期：2026-07-24

## 1. 项目目标

本项目用于批量分析网球训练视频，自动过滤持续时间较短的对打片段，只保留持续时间较长、值得人工复选的回合，并将每个回合独立编码为视频文件。

第一版的主要目标如下：

- 输入单个视频或包含多个视频的文件夹。
- 同时利用声音和画面判断当前是否处于连续对打状态。
- 默认只保留有效对打时间不少于 10 秒的回合。
- 每段视频默认在回合开始前保留 2 秒、结束后保留 3 秒。
- 自动保留源视频的分辨率、有效帧率、画面方向和音画同步关系。
- 使用 NVIDIA GeForce RTX 4060 Laptop GPU 加速视觉推理和 HEVC 编码。
- 使用 `uv` 管理 Python 环境、依赖和命令执行。
- 生成视频片段、CSV 报告、JSON 分析记录和处理日志。
- 永不修改、移动或删除源视频。

第一版不追求精确统计双方总击球次数，也不要求准确区分正常回球、下网、落地和出界。筛选标准以“连续有效对打时长”为主。

## 2. 已知输入条件

当前样片为：

- 文件：`网球/VID_20260425_213428.mp4`
- 时长：约 22 分 13 秒
- 视频：HEVC，3840×2160，约 30 FPS
- 音频：AAC，48 kHz，双声道
- 机位：云台固定在球场侧后方，画面可能随云台产生小幅方向变化
- 主体：近端球员在画面中占比较大，以正手动作和近端球员表现为主
- 环境：夜间灯光较强，背景包含其他球场、球员和击球声

后续输入还可能包含苹果设备拍摄的 1080P 30 FPS 或 1080P 60 FPS 视频，因此处理流程不能假定输入一定是 4K 或固定帧率。

## 3. 方案选择

第一版采用“音频产生候选事件，视觉验证近端动作，时间序列推断回合状态”的多模态方案。

不采用以下两种极端方案：

- 纯音频方案：容易把相邻球场击球声、脚步声和其他瞬态噪声误判为当前回合。
- 纯网球轨迹方案：网球高速、尺寸小、存在运动模糊，当前侧后方竖屏夜间素材与公开广播机位数据差异较大，第一版直接使用 TrackNet 类模型的投入和风险较高。

多模态融合不使用机械的“声音与画面必须同时出现”规则。近端击球应由声音和动作共同确认；远端对手可能不在画面中，因此允许通过声音、击球间隔和近端球员准备动作推断远端击球。

## 4. 总体架构

处理流程如下：

```text
扫描输入视频
    ↓
读取媒体元数据
    ↓
┌──────────────────┬──────────────────┐
│ 音频候选事件检测 │ 近端球员动作检测 │
└──────────────────┴──────────────────┘
              ↓
         音画事件融合
              ↓
      连续对打状态机判断
              ↓
   时长过滤、缓冲和区间合并
              ↓
      NVENC 精确编码切片
              ↓
 视频片段、CSV、JSON 和日志
```

建议的模块边界如下：

- `scanner`：扫描输入路径并读取视频元数据。
- `audio`：提取音频特征并输出带时间戳的声音候选事件。
- `vision`：跟踪主球员并输出动作和运动置信度。
- `fusion`：融合音频、视觉和事件间隔信息。
- `segmenter`：使用状态机生成候选回合区间并应用筛选规则。
- `exporter`：调用 FFmpeg 和 NVENC 输出最终片段。
- `report`：保存结构化分析数据、验证结果和错误信息。
- `cli`：提供输入路径、输出路径和处理进度入口。

各模块通过带时间戳的数据结构通信，避免音频、视觉和编码逻辑互相耦合。

## 5. 媒体扫描与输入处理

程序接受单个视频文件或文件夹。输入文件夹按需递归扫描以下格式：

- `.mp4`
- `.mov`
- `.mkv`
- `.m4v`

每个视频首先通过 `ffprobe` 读取：

- 视频和音频编码格式
- 分辨率和像素格式
- 平均帧率、时间基和总时长
- 旋转元数据
- 色彩空间、传递函数和色彩范围
- HDR10 或 Dolby Vision 标记
- 是否包含可用音轨

媒体扫描失败时只跳过当前文件，不终止整个文件夹任务。

## 6. 音频候选事件检测

音频分析在 CPU 上执行，不占用 GPU 显存。处理步骤如下：

1. 使用 FFmpeg 将音轨临时转换为单声道 PCM。
2. 计算 Log-Mel 频谱。
3. 计算多频段频谱通量，突出短促的能量突变。
4. 根据当前视频的背景噪声建立动态阈值。
5. 对峰值进行最小间隔约束和去重。
6. 输出声音候选事件的时间戳、强度、频谱特征和置信度。

第一版不将单次声音强制分类为“正常击球”“下网”“落地”或“出界”。这些声音先统一作为瞬态候选，再由视觉信息、前后事件间隔和回合状态决定其作用。

相邻球场声音通常没有对应的近端挥拍动作，而且与当前球员的动作节奏不一致，因此会在融合阶段降低权重。

## 7. 视觉动作检测

视觉分析使用 CUDA 加速，但不会以原始 4K 分辨率逐帧推理。处理步骤如下：

1. 按配置的分析帧率抽取画面。
2. 将分析画面等比例缩放到约 720P，最终输出仍使用原视频分辨率。
3. 使用轻量人体姿态模型检测人物关键点。
4. 根据人物面积、画面位置和连续轨迹选择近端主球员。
5. 在检测帧之间跟踪主球员，减少重复检测开销。
6. 估计全局画面运动，抵消云台调整造成的共同位移。
7. 计算肩、肘、腕的角速度、手臂加速度、身体重心移动和局部光流。
8. 输出近端挥拍候选、准备动作、持续运动量和视觉置信度。

背景球场中的球员通常面积较小，不应参与主球员动作判断。如果主球员丢失时间过长，则当前区间降低置信度，而不是自动选择背景中的其他人物。

## 8. 音画事件融合

融合模块按时间窗口对齐声音和视觉事件：

- 声音峰值与近端挥拍在约 ±0.3 秒内出现：高置信度近端击球。
- 只有声音，但与上一击时间间隔合理：中等置信度远端击球候选。
- 只有挥拍，没有明显声音：中等偏低置信度，可能是空挥或录音较弱。
- 只有背景击球声，近端球员没有对应动作或准备状态：低置信度。
- 近端球员持续移动和准备动作：可以维持回合状态，但不单独记作击球事件。

事件融合应保留原始分数和判定理由，便于后续根据误检片段调节参数。

## 9. 回合状态机与切分规则

状态机包含四种状态：

```text
IDLE → CANDIDATE → ACTIVE → END_PENDING → IDLE
```

- `IDLE`：没有可靠的当前回合。
- `CANDIDATE`：出现初始音画事件，但尚不足以确认连续对打。
- `ACTIVE`：音画事件和球员活动持续出现，认为正在对打。
- `END_PENDING`：短时间没有新事件，等待确认是短暂漏检还是回合结束。

当连续无可信事件且球员运动量降低的时间超过结束间隔时，回合在最后一个可信事件附近结束。相邻候选区间的间隔小于合并阈值时自动合并，避免偶发漏检将一个长回合切成两段。

有效对打时间达到最短回合时长后才输出。最终切点加入回合前后缓冲，并限制在源视频有效时间范围内。

## 10. 可调参数与中文注释规范

所有用户可能调整的参数必须集中在单独的 Python 配置对象中。每个参数定义后必须紧跟中文注释，注释必须同时说明：

- 参数控制什么行为；
- 调大后的效果；
- 调小后的效果；
- 可能增加的误检或漏检风险。

第一版配置形式如下：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class AnalysisConfig:
    min_rally_duration: float = 10.0  # 最短有效对打时长，调大后只保留更长回合但可能漏掉精彩短回合，调小后输出更多但短回合也会增多
    pre_roll: float = 2.0  # 回合开始前保留秒数，调大后准备动作更完整但片段更长，调小后更紧凑但可能切掉引拍前内容
    post_roll: float = 3.0  # 回合结束后保留秒数，调大后能保留收拍和反应但片段更长，调小后更紧凑但可能结束过急
    end_silence: float = 3.0  # 无可信击球后等待多久判定回合结束，调大后不易误断长回合但可能把间歇并入回合，调小后切分更敏感但容易把长回合拆开
    merge_gap: float = 1.5  # 两个候选区间间隔小于该值时自动合并，调大后更容易合并误断片段但也可能粘连两个独立回合，调小后区分更严格但漏检时容易碎片化
    analysis_fps: int = 12  # 每秒分析的画面帧数，调大后动作定位更细但推理更慢且显存占用增加，调小后速度更快但可能漏掉快速挥拍
    audio_sample_rate: int = 22050  # 音频分析采样率，调大后保留更多高频细节但计算量增加，调小后分析更快但可能削弱击球瞬态特征
    audio_sensitivity: float = 1.0  # 声音候选灵敏度，调大后能检出更弱击球但背景球场误检会增加，调小后误检减少但可能漏掉远端或较轻的击球声
    visual_sensitivity: float = 1.0  # 挥拍动作灵敏度，调大后更容易识别轻微动作但空挥误检会增加，调小后判断更严格但可能漏掉幅度较小的回球
    fusion_threshold: float = 0.6  # 音画融合后判定可信事件的最低分数，调大后结果更保守但可能漏检，调小后召回率提高但背景噪声误检会增加
    encode_cq: int = 21  # NVENC 恒定质量参数，数值调小后画质更高且文件更大，数值调大后文件更小但压缩痕迹更明显
```

实现时不得使用没有中文解释的裸数字替代这些配置参数。内部算法常量若不适合用户调整，应封装在对应模块中，不暴露为公共配置。

## 11. 视频输出

输出阶段使用 FFmpeg 精确切分，并使用 RTX 4060 Laptop GPU 的 `hevc_nvenc` 编码。

输出原则如下：

- 不主动升高或降低分辨率。
- 不主动将 30 FPS 改为 60 FPS，也不将 60 FPS 改为 30 FPS。
- 保留原始时间关系和音画同步。
- 保留原始画面方向，正确处理苹果视频的旋转元数据。
- SDR 视频按 HEVC 8-bit 编码。
- HDR10 视频按 HEVC Main10 编码并保留必要色彩参数。
- 检测到 Dolby Vision 时第一版停止处理该文件并明确警告，避免静默丢失动态元数据或产生偏色。
- NVENC 不可用或显存不足时明确报错，不静默切换为软件编码。

建议的输出结构如下：

```text
精选输出/
└── VID_20260425_213428/
    ├── clips/
    │   ├── rally_001_00-02-14_12.6s.mp4
    │   ├── rally_002_00-05-47_18.3s.mp4
    │   └── ...
    ├── segments.csv
    ├── analysis.json
    └── processing.log
```

文件名包含序号、源视频时间位置和有效回合时长，便于人工复选。

## 12. 报告内容

`segments.csv` 面向人工查看，至少包含：

- 片段文件名
- 回合开始和结束时间
- 加入缓冲后的输出开始和结束时间
- 有效对打时长
- 声音候选事件数量
- 近端挥拍候选数量
- 平均融合置信度
- 输出验证状态

`analysis.json` 保存更完整的机器可读数据，包括每个候选事件的时间戳、来源、分数和判定理由，以支持后续调参和算法升级。

## 13. 错误处理与安全规则

- 没有音轨：停止处理当前视频并说明第一版需要音画融合。
- 无法稳定找到主球员：跳过当前视频并记录原因。
- 媒体文件损坏：记录 FFmpeg 或 ffprobe 错误，不生成不完整片段。
- Dolby Vision：停止当前视频并提示色彩兼容风险。
- NVENC 不可用：停止编码并提供检查命令。
- 单个视频失败：继续处理同一文件夹内的其他视频。
- 输出路径已存在：创建明确的新任务目录或拒绝覆盖，不静默覆盖旧结果。
- 源视频始终以只读方式使用，程序不包含删除、移动或原地覆盖源视频的逻辑。

## 14. 输出验证

每个输出片段生成后执行以下检查：

1. 使用 `ffprobe` 确认文件可读取。
2. 确认视频流和音频流存在。
3. 检查分辨率、帧率和像素格式是否符合源视频策略。
4. 检查输出时长与计划切点是否在容差范围内。
5. 对片段开头和结尾执行解码检查。
6. 只有验证成功的片段才写入最终成功列表。

验证失败的片段保留错误日志，但不得被标记为可安全保留的精选结果。

## 15. 测试策略

### 15.1 单元测试

- 状态机从空闲到活动再到结束的转换。
- 10 秒最短回合阈值的边界情况。
- 前后缓冲不得超出源视频范围。
- 相邻片段合并和不合并的边界情况。
- 音频事件和视觉事件时间对齐。
- 配置参数验证，包括负数、零值和不合理范围。

### 15.2 集成测试

- SDR 1080P 30 FPS 视频。
- SDR 1080P 60 FPS 视频。
- SDR 4K 30 FPS 视频。
- 无音轨视频。
- 旋转元数据视频。
- HDR10 和 Dolby Vision 检测。
- 背景球场击球声较多的素材。
- 主球员短暂离开画面的素材。

### 15.3 真实样片校准

从当前视频人工标记约 5 至 10 分钟，记录实际长回合的起止时间，作为第一版校准集。

初期优化方向以召回率为主：允许输出少量疑似片段，但尽量不漏掉持续时间超过阈值的真实长回合。初步验收目标为长回合召回率约 90%，具体参数在真实标注结果基础上调整。

## 16. 性能策略

- 音频分析使用 CPU。
- 姿态模型和必要的视觉推理使用 CUDA。
- 分析阶段使用缩小画面和较低分析帧率。
- 原始分辨率只在最终切片编码阶段使用。
- 视频解码和编码尽可能使用 NVDEC 与 NVENC。
- RTX 4060 Laptop GPU 只有 8 GB 显存，视觉推理使用轻量模型和小批次，避免同时驻留多个大型模型。
- 同一时间默认只处理一个高分辨率视频，第一版不并行编码多个 4K 视频。

## 17. 第一版非目标

以下功能不纳入第一版：

- 自动删除或移动源视频。
- 图形界面。
- 精确统计双方总击球次数。
- 自动生成精彩程度评分或排行榜。
- 准确判断得分、下网、出界或落点。
- 专用网球轨迹模型训练。
- 云端上传或在线服务。

这些功能只有在第一版真实样片效果验证后，才根据实际需要决定是否增加。

## 18. 完成标准

第一版实现完成需同时满足：

- 能通过 `uv` 完成环境同步和命令运行。
- 能批量读取当前约定的视频格式。
- 能生成音频候选、视觉动作和融合事件记录。
- 能自动找出持续时间达到配置阈值的候选回合。
- 能按配置加入前后缓冲并合并短暂误断。
- 能通过 NVENC 输出保持源分辨率和帧率策略的视频片段。
- 能生成 CSV、JSON 和日志。
- 能验证输出片段可读取且音画流完整。
- 不修改、移动或删除任何源视频。
- 所有用户可调参数都带有紧跟参数定义的中文效果注释。
